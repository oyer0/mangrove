# Filesystem qualification foundation

The Mangrove Filesystem Qualification Suite (MFQS) compares production
filesystem results with an independent Python byte/offset/namespace model.
The routine profiles qualify fixed MGFS, FAT32 and exFAT operations on
disposable regular-file images. This is a foundation, not complete filesystem,
storage, recovery, hardware or crash qualification.

## Production integration and boundaries

`tests/mfqs/runner.py` compiles complete, unmodified `kernel/src/vfs.c` and
the selected `kernel/src/storage/{mgfs,fat32,exfat}.c` translation unit with
ASan/UBSan. exFAT also links complete production `libc/src/time_convert.c`.
There is no
function extraction, source patching or replacement of filesystem allocation,
lookup, checksums, metadata publication, reclamation or recovery algorithms.
The adapter calls public VFS mount, ordinary/exclusive-create, open, read, write, seek,
metadata, checked enumeration, close and unmount APIs. Empty exclusive creation
exercises the actual recovery-pin registry and filesystem post-unlock handoff;
observations require zero outstanding pins after each operation.

`tests/mfqs/host.c` provides bounded host heap, regular-file block I/O,
single-threaded lock assertions and one immutable device descriptor. Process
context is the trusted kernel context with no working-directory references.
Credential and partition-specific callbacks abort if reached. These controlled
services do **not** test process authorization, scheduler synchronization,
block cache/registry races, partition management, DMA or physical devices.
Production VFS lifetime and recovery logic remain in use.
FAT32/exFAT flush callbacks perform actual host `fsync`. Raw formatter and
management callbacks abort if reached; independent tools prepare the images.
exFAT receives an explicit simulated trusted UTC clock at 2000-01-01 00:00:00
with whole-second precision. This neither detects RTC trust nor changes
production clock policy. Timestamp encoding/validation still runs in production.

A clean remount closes all file handles, invokes real VFS unmount/driver
disposal, verifies mount-private allocations were released and cached nodes
became inert, closes/syncs the image descriptor, reopens it, and mounts anew.
Readback then uses freshly discovered records. VFS intentionally retains
long-lived cached nodes after detach; the host releases only verified inert
nodes at final process exit and requires all other allocations to be gone.
This is host cleanup after production teardown, not a substitute for teardown.
Host `fsync` and image reopening do not establish target crash durability.

## Qualified profile and unsupported coverage

| Operation | MGFS fixed foundation | FAT32/exFAT fixed profiles |
| --- | --- | --- |
| Empty exclusive create; open/close/reopen | Covered | Covered |
| Ordinary public VFS creation | Not in the fixed trace | Covered separately from exclusive creation |
| Append, prefix/middle overwrite, zero-byte write | Covered, exact suffix/length preservation | Covered, exact suffix/length preservation |
| Seek/read/EOF and lengths/offsets | Covered | Covered, including zero-filled gaps |
| Root membership and missing/existing-name conflicts | Covered, case-sensitive ASCII names | Covered, ASCII case-insensitive conflicts and mixed-case opens |
| Clean remount and refusal with an open handle | Covered | Covered |
| Poisoned allocation slack and free clusters | Not in the fixed trace | Covered |
| DataLength greater than ValidDataLength | Not applicable | exFAT fragmented imported stream covered |
| Resize, safe replacement, rename, unlink, mkdir/rmdir | Not qualified | Not qualified |
| Broader imported layouts, Unicode, faults, concurrency, guest boot | Not qualified | Not qualified |

The MGFS trace retains its 98 commands and two successful remounts. It starts
with an empty MGFS 1.2 volume generated by the repository's `mkmgfs`, using
3,200 blocks, UUID `11111111-2222-3333-4444-555555555555`, and format time `1`.
It crosses inline storage, the 4 KiB boundary and the 8 KiB boundary, reaching
8,193 bytes. Byte patterns are independently specified in Python. Namespace
comparison ignores enumeration order but preserves duplicates and counts.
Structural checkers supplement the byte oracle; they cannot prove content safety.

FAT32/exFAT empty profiles contain 135 commands; imported profiles contain 167.
Each includes two successful remounts. FAT32 uses a standards-sized 64 MiB,
two-FAT volume with 512-byte clusters, built by `mkfs.fat --invariant` with
serial `12345678`. exFAT uses a 6,144,000-byte one-FAT volume with 4 KiB clusters,
built by `mkfs.exfat`. A bounded independent fixture encoder normalizes exFAT
serial/checksum fields and uses unknown utilization (0xFF), making the initial
image deterministic. It does not service any runtime filesystem operations.
All free clusters are poisoned with 0x5A. Imported allocated slack is 0xA5.

`--layout slack` imports `old.txt` with four readable bytes, then checks writes
at offsets 16 and 4196 against exact zero-gap expectations before and after
remount. exFAT additionally supports `chained-slack` (one-cluster FAT chain)
and `short-valid` (two nonadjacent clusters, DataLength 8000, ValidDataLength 4).
The latter's logical tail begins as zero despite poisoned storage and stays
correct when ValidDataLength advances. Imported dates are 2000-01-01 00:00:00;
exFAT encodes valid zero UTC offsets, while FAT32 has no timezone fields.
Images are independently checked before
production mounting and after teardown. This is a small fixed layout set,
not a general imported-image compatibility matrix.

Missing backend tooling or unsupported fixture layouts report **INCOMPLETE**
and exit 2. A model mismatch,
adapter failure, timeout or image-check failure reports **FAIL** and exits 1.
Successful fixed-profile comparison reports **PASS** and exits 0, accompanied
by the explicit unqualified coverage list. Dependency, build and invalid replay
inputs report INCOMPLETE; they cannot become a green qualification result.
The broad qualification campaign remains incomplete even when this profile
passes. Existing recovery and storage regressions continue separately in the
normal host suite; MFQS does not replace or summarize them as its own coverage.

## Protocol, model and replay

`tests/mfqs/model.py` uses Python bytes and a pathname dictionary; it never
parses disk metadata or imports driver algorithms. Ordinary writes publish
`max(old length, written end)` and preserve unaffected bytes. FAT32/exFAT
gap writes add zero bytes; MGFS sparse writes remain outside its profile. The
foundation is deterministic and has no random seed or generated campaign.

MFQS1 requests are five tab-separated fields:
`MFQS1`, ascending sequence, operation, first argument, second argument.
Paths and payloads use lowercase hexadecimal; `-` represents an empty or
unused argument. Responses contain eight fields: version, sequence, VFS
status, file length, offset, transferred/type/member count, recovery-pin count,
and hexadecimal data. HELLO declares the backend/profile and differences in
name, gap and resize policy. FAT32's operation table supports arbitrary resize;
exFAT/MGFS support truncate-to-empty but reject nonzero arbitrary resize.
Resize declarations describe the driver, not a tested transport operation.
CREATE uses exclusive empty creation; CREATE_ORDINARY separately calls public
`vfs_create` and then `vfs_open_node`. STAT
and LIST return operation-specific metadata rather than active-handle offsets.
Malformed envelopes, reordered/missing responses and incomplete enumeration
cannot satisfy the model. Public VFS status constants are an ABI expectation,
not inferred from observed failures.
MFQS preserves raw VFS statuses, including UNSUPPORTED, UNCERTAIN and
TIME_UNAVAILABLE, instead of flattening them into a generic errno or EOF.
Unexpected refusal of an advertised operation is FAIL, not successful coverage.
The existing byte-count read interface still lacks detailed error classification;
the fault-free profile detects unexpected short content through its oracle.
ASCII membership comparisons normalize case only for FAT32/exFAT, retain
duplicate counts, and do not claim to qualify Unicode folding or name presentation.

Each run is bounded to 256 commands, one file handle, 8 KiB per transfer,
64 KiB per file, 31 root names, 64 MiB per image, 8 MiB requested kernel heap,
1,024 live heap allocations and 512 retained node slots. The adapter has a
60-second subprocess timeout; compiles have a 120-second timeout. Output
inspection is capped at 5 MiB. These are harness bounds, not filesystem limits.
There is no automatic minimizer. The report identifies the first mismatching
operation and preserves the complete replayable trace and observations.

## Commands and artifacts

On Linux use GCC and `make`; on macOS use native Homebrew GCC and `gmake`:

```sh
gmake test-mfqs
python3 tests/mfqs/runner.py --cc gcc-16
python3 tests/mfqs/runner.py --cc gcc-16 --artifacts /tmp/mfqs-example
python3 tests/mfqs/runner.py --cc gcc-16 --replay /tmp/mfqs-example/report.json
python3 tests/mfqs/runner.py --cc gcc-16 --negative-control byte
python3 tests/mfqs/runner.py --cc gcc-16 --negative-control length
python3 tests/mfqs/runner.py --cc gcc-16 --backend fat32 --layout slack
python3 tests/mfqs/runner.py --cc gcc-16 --backend exfat --layout short-valid
```

An explicit artifact directory must be new. The CLI deletes its disposable
temporary directory only after PASS; FAIL/INCOMPLETE retain available evidence.
Artifacts include original and resulting images, commands, observations,
adapter stderr, first mismatch, complete expectations, source/binary/image
SHA-256 hashes, formatter arguments, compiler, platform and checkout identity.
Replay rebuilds the current production backend and regenerates the initial
image, requiring the original image hash to match. It recomputes the model
instead of trusting saved expectations. Negative controls must be requested
explicitly on replay; historical source requires its historical backend build.

FAT32 requires `mkfs.fat` and `fsck.fat`; exFAT requires regular-file-capable
`mkfs.exfat` and `fsck.exfat`. Tools are discovered on PATH and /usr/sbin.
Absent dependencies retain explicit per-backend INCOMPLETE results, and
`test-mfqs` returns failure rather than counting the backend as passed.
CLI compatibility adapters, where needed for exfat-utils, must be reported;
formatter commands/output and executable hashes are recorded in provenance.

`tests/mfqs_test.py` checks each positive profile, byte and length negative
controls, replay determinism, protocol rejection and visible missing-backend
reporting. It also compiles immutable historical MGFS commit
`487b9bdd6a536820c2f2ffcddcca691568c7de23` with the current VFS/host adapter:
the oracle detects its successful prefix overwrite shrinking 4,096 bytes to
one byte. Incorrect oracle-byte and oracle-length controls report FAIL even
though the resulting image passes structural checking. Regression-test PASS
means those failures were correctly detected, not that defective results passed.
The exFAT control similarly compiles immutable historical commit
`cb29138da7d20f1b0ea3cd96f86e6682d7752311`; writes return success with resolved
pins, but readback exposes poisoned slack at lengths 17 and 4197 and the model
reports FAIL. These controls require the historical commits to be available locally.

## Costs and portability

Measured on native Apple Silicon GCC with dosfstools 4.2 and exfat-utils 1.4
(its formatter CLI adapted to accept exfatprogs-style cluster-size arguments):

| Profile | Commands | Driver reads | Writes | Flushes | Heap requests | Peak requested kernel heap |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| MGFS empty | 98 | 242 | 45 | 0 | 104 | 95,824 bytes |
| FAT32 empty | 135 | 732 | 136 | 28 | 477 | 9,672 bytes |
| FAT32 slack | 167 | 895 | 192 | 34 | 556 | 9,808 bytes |
| exFAT empty | 135 | 621 | 125 | 56 | 125 | 23,460 bytes |
| exFAT slack | 167 | 741 | 157 | 66 | 146 | 24,372 bytes |
| exFAT chained-slack | 167 | 753 | 159 | 66 | 147 | 24,372 bytes |
| exFAT short-valid | 167 | 854 | 151 | 64 | 145 | 24,372 bytes |

After final unmount, 12 inert nodes (864 bytes) remain in the empty FAT32/exFAT
profiles and 15 (1,080 bytes) in imported profiles and MGFS; they are reaped at
exit. No transaction or driver-private allocations remain. Counts depend on
the initial layout/tooling and are measurements, not cross-filesystem budgets.
Driver calls can cover multiple sectors and are not
physical-device I/O counts. Reports include adapter CPU/wall time separately
from compilation and checker execution; timings are host-dependent.
Protocol, model and host-tool memory are outside the requested kernel heap.
Two image files are retained per artifact run: each is 13,107,200 bytes for
MGFS, 67,108,864 bytes for FAT32 or 6,144,000 bytes for exFAT. Fixture encoding
uses a bounded mmap and free-cluster inventory; it is outside the driver heap.
The complete routine regression can temporarily retain about 1.5 GiB across
positive, replay and negative controls before cleanup. CLI runs only the
selected profile. FAT32's final checker can report an uninitialized free-cluster
summary because runtime transactions legitimately invalidate advisory FSInfo
hints; the checker exits zero and its warning is preserved, not suppressed.

Native Apple Silicon GCC ASan/UBSan runs without target-source adaptations.
The C adapter uses POSIX regular-file I/O and the build uses GCC on both
Darwin and Debian, with no platform-specific filesystem source changes or
GNU-only linker flags. Linux execution still needs independent verification
when not available on the development host. The normal macOS host suite's
existing x86 `rdtsc` clock fixture cannot compile on ARM; this remains separate
from MFQS results. No guest/QEMU or hardware validation is implied.

Broader operations, independently imported
layouts, deterministic sequence generation, fault profiles and recovery
qualification require deliberate extensions with visible capability coverage.
